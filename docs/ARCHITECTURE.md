# Архитектура bare_app

## Цели

1. Своё приложение для SDK с выводом через LVGL; первая платформа — ODROID-GO Advance
   (экран, кнопки, стик).
2. Новая плата или новое оборудование добавляются без переделки остального кода.
3. LVGL отвечает только за отрисовку и может быть заменён другим тулкитом.

## Слои

```
┌──────────────────────────────────────────────────────────────────┐
│ gui/view/<backend>   виджеты и экраны тулкита (lvgl, headless)    │  единственное место с LVGL
├──────────────────────────────────────────────────────────────────┤
│ gui/view/core        поток view: снимки контекста, подписки,      │  без тулкита
│                      геймпад → UI-клавиши, захват ввода           │
├──────────────────────────────────────────────────────────────────┤
│ gui/ctx · action · notify   граница между control и view          │  без тулкита
├──────────────────────────────────────────────────────────────────┤
│ gui/control          модули по областям данных: питание, экран,   │  без тулкита
│                      звук, Wi-Fi, навигация, система              │
├──────────────────────────────────────────────────────────────────┤
│ services · core      шина событий, главный цикл, очереди,         │
│                      логический геймпад, математика стика         │
├──────────────────────────────────────────────────────────────────┤
│ hal (интерфейсы) · drivers (реализации) · platforms (таблицы)     │
└──────────────────────────────────────────────────────────────────┘
```

Границу с тулкитом держит сборка: путь к заголовкам LVGL подключён только к цели
`bare_app_view_lvgl`. Подключение `lvgl.h` в любом другом месте ломает сборку.
Бэкенд `headless` собирается вообще без тулкита и служит проверкой этой границы.

## Потоки

| Поток | Владеет | Ждёт в `poll()` |
|---|---|---|
| control (main) | сервисы, шина, модули control, запись в контекст | signalfd, очередь шины, очередь действий, таймеры сервисов |
| view | LVGL, драйверы экрана и ввода, подписки view, видео-слой | eventfd контекста, очередь notify, evdev, DRM, ящик кадров, таймеры LVGL |
| источники видео | свой буфер в ящике кадров | свой темп (камера, таймер) |
| процесс `bare_app_doom` | движок Doom, свой буфер в общей памяти | свой цикл, 35 тиков/с |

Потоки control и view работают каждый на своём экземпляре `core/mainloop`. Между
потоками общих объектов пять, все потокобезопасные:

- контекст `gui_ctx` (мьютекс; view читает только снимки);
- очередь действий view → control (`gui_action_post`);
- очередь уведомлений control → view (`gui_notify_post`);
- шина событий: сервисы → control (`bus_post`, можно из любого потока);
- ящик кадров: источник видео → view (`media/mailbox`).

Сигналы (SIGINT, SIGTERM, SIGHUP) заблокированы во всех потоках и принимаются
через `signalfd` в потоке control. Если программа упадёт по SIGSEGV и т. п.,
драйвер fbdev вернёт консоль в `KD_TEXT`.

## Поток данных

```
 сервис ──bus──► control-модуль ──ctx_lock/unlock──► gui_ctx ──снимок──► подписки view ──► LVGL
                       ▲                                                     │
                       └───────────────── gui_action_post ◄──────────────────┘
                       └──► gui_notify_post ──► view (тосты, без склейки)
```

- **Контекст** — это снимок состояния, в нём только значения: проценты, флаги,
  `enum`. Цвета, иконки и готовый текст в контекст не кладутся. Секции
  (`CTX_POWER`, `CTX_DISPLAY`, `CTX_NAV`, `CTX_SYSTEM`, `CTX_SETTINGS`, `CTX_AUDIO`,
  `CTX_WIFI`, `CTX_USB_DISK`, `CTX_SYSMON`) — единицы изменения.
  `ctx_unlock(mask)` будит view, а view берёт снимок один раз за итерацию. Поэтому
  несколько записей между двумя кадрами приходят как одно изменение с последними
  значениями.
- **Действия** — единственный способ для view что-то изменить. В контекст view
  не пишет.
- **Уведомления** — разовые события («батарея разряжена», «зарядка подключена»).
  Они не склеиваются, доставляется каждое.
- **Ввод** через контекст не идёт. Поток view сам читает evdev: навигацию передаёт
  в тулкит, а глобальный хоткей выхода — в control как действие. Экран может
  захватить сырой геймпад (`view_input_grab`), так работает тест ввода.

## Модули control

control делится по областям данных, а не по виджетам: каждый модуль пишет только
свою секцию.

| Модуль | Слушает | Пишет |
|---|---|---|
| `ctl_app` | `ACT_QUIT`, `ACT_POWER_OFF` | останавливает цикл control; после `ACT_POWER_OFF` main() запускает `poweroff` платформы, если он есть |
| `ctl_nav` | `ACT_OPEN_SCREEN`, `ACT_BACK` | `CTX_NAV` (стек экранов) |
| `ctl_system` | — | `CTX_SYSTEM` (платформа, модель из DT) |
| `ctl_power` | `EV_POWER_CHANGED`, `ACT_SUSPEND` | `CTX_POWER`, уведомления; для `ACT_SUSPEND` запускает `suspend` платформы и ждёт пробуждения, затем `NOTIFY_RESUMED` |
| `ctl_display` | `ACT_SET_BRIGHTNESS`, `ACT_SCREEN_OFF` | `CTX_DISPLAY` (то, что подсветка реально приняла); экран гасится питанием подсветки (`bl_power`), уровень сохраняется |
| `ctl_audio` | `EV_MIXER_CHANGED`, `ACT_SET_VOLUME`, `ACT_VOLUME_STEP`, `ACT_SET_AUDIO_OUT` | `CTX_AUDIO`, `NOTIFY_VOLUME`; в режиме «авто» переключает выход по штекеру |
| `ctl_wifi` | `EV_WIFI_*`, `ACT_WIFI_*` | `CTX_WIFI` (связь, адрес, сети рядом), уведомления о подключении и неверном ключе |
| `ctl_usb_disk` | `ACT_OPEN_SCREEN`, `ACT_BACK`, `ACT_USB_DISK` | `CTX_USB_DISK`; открывает раздел с играми компьютеру командой платформы |
| `ctl_sysmon` | `ACT_SYSMON` | `CTX_SYSMON`: пока монитор открыт, раз в секунду замер `services/sysmon.c` |

Каркас модуля: `struct control_ops { init, on_action, deinit }` (gui/control/control.h).

## Виджеты view

Каркас виджета (gui/view/lvgl/widget.h):

```c
struct widget_ops {
	const char *name;
	uint32_t deps;                                          /* секции контекста */
	void *(*init)(lv_obj_t *parent, lv_obj_t **root);       /* создать объекты */
	void  (*update)(void *self, const struct gui_ctx *ctx, uint32_t changed);
	void  (*deinit)(void *self);
};
```

- `widget_create()` вызывает `init`, подписывает `update` на `deps` (первый вызов
  сразу, с `CTX_ALL`) и привязывает отписку и `deinit` к удалению корневого объекта.
- `update` сравнивает новое значение с показанным и только при отличии вызывает
  `lv_*_set_*`: каждый вызов set перерисовывает область.
- Экраны тоже виджеты. Менеджер экранов следит за `CTX_NAV` и даёт каждому экрану
  свою группу фокуса.
- Один виджет можно ставить на несколько экранов: строка состояния
  (`statusbar_create`) стоит на всех.

## HAL, драйверы, платформы

- **hal/hal.h** — интерфейсы: дисплей со слоями (`LAYER_VIDEO`, `LAYER_UI`,
  `LAYER_OSD`), ввод, питание, подсветка, микшер, Wi-Fi. Буфер слоя хранится в логической
  ориентации, формат (XRGB или ARGB) выбирает драйвер, поворот делает драйвер.
  Необязательная операция `snapshot` пишет сложенные слои в PPM.
- **drivers/** — реализации:
  - `display_drm` — DRM/KMS на голых ioctl ядра (без libdrm): UI на overlay-плоскости
    в ARGB, видео на primary, по два dumb-буфера на слой, nonblocking atomic commit
    не чаще одного на vblank (событие flip в цикле view), поворот и premultiply при
    копировании изменённых областей (`blit.c`). Если overlay с RGB нет (GO Ultra:
    плоскость Amlogic для видео берёт только YUV), видеослой — только теневой буфер:
    `blit_compose()` кладёт UI поверх него в обычной памяти, затем поворот в буфер
    primary (из буферов сканирования не читаем: они часто некэшируемые);
  - `display_fbdev` — один слой UI, поворот как у fbcon; запасной вариант, если DRM
    занят или его нет;
  - `display_mem` — экран в памяти для тестов, у платформы `pc-mem` с видео-слоем
    под UI, как на OGA;
  - `sdl` — окно и клавиатура симулятора (платформа `pc`);
  - `input_evdev` — поиск по имени, раскладка, оси по диапазону `EVIOCGABS`
    (положение при открытии — покой стика), оси стика вместе по `SYN_REPORT`,
    hotplug по uevent; `input_script` — сценарий кнопок из stdin;
  - `sysfs` — батарея и подсветка; `console.c` — KD_GRAPHICS и его возврат, в том
    числе при падении;
  - `mixer_alsa` — ioctl управляющего устройства ALSA без alsa-lib: регуляторы по
    имени, кривая громкости по dB-диапазону (как в alsamixer, `core/volume.c`), выбор
    выхода, штекер, события изменений;
  - `wifi_wpa` — управляющий сокет `wpa_supplicant` без libwpa_client: запросы с
    таймаутом и второй сокет (ATTACH) для событий;
  - `sim` — имитация микшера и Wi-Fi для платформ ПК.
- **platforms/** — только данные: какие драйверы и с какими параметрами.
  `platform_probe()` выбирает платформу по `/proc/device-tree/compatible`.
  Дисплеев в платформе можно указать несколько, открывается первый рабочий
  (на OGA: DRM, затем fbdev).
  Поэтому ревизии OGA 1.0, 1.1 и Super работают из одного бинарника, а размер
  экрана берётся у драйвера.

Логический геймпад (core/input) отделяет физические коды от смысла:
evdev-код → `GP_*` (раскладка платформы) → UI-клавиша (view core) → `LV_KEY_*` (бэкенд).
Стики калибруются здесь же, целиком, а не по осям (`core/joystick`): положение
покоя, ход каждой полуоси, край, приведённый к окружности по 16 направлениям, и
круглая мёртвая зона. Калибровку снимает тест ввода (A дважды: стики в покое,
затем обвести край) и пишет в `bare_app_sticks.conf` рядом с файлом настроек;
без неё — покой при открытии и диапазон драйвера. Игры получают уже
откалиброванные оси.
Стик превращается в виртуальную крестовину с гистерезисом. Автоповтор направлений
делается здесь же, а не в LVGL: indev LVGL работает в режиме событий, без опроса.

## Видео-слой

Слой `LAYER_VIDEO` лежит под UI. Экран, который показывает видео, делает свой фон
прозрачным и выбирает источник через ядро view: `view_video_set(VIDEO_TEST_PATTERN)`.

Источники работают в своих потоках и отдают кадры через `media/mailbox`:

```
поток источника ── mailbox_begin / mailbox_end ──► mailbox (3 буфера) ── eventfd ──►
поток view: mailbox_take → копия в слой → damage / submit → DRM-плоскость
```

Источник никогда не ждёт. Непрочитанный кадр заменяется более новым, и для видео
это правильно: важен последний кадр. Пока источник один — `media/testpattern.c`,
поток с собственным темпом кадров. Камера (V4L2) или GPU-рендер подключаются так же.
Чтобы избежать лишней копии, им понадобится импорт dmabuf прямо в плоскость.

Если видео-слоя нет (fbdev, SDL), `view_video_available()` возвращает false, и экран
показывает сообщение. Пример — экран «Layers».

## Игры в отдельном процессе

Все игры — один источник видео `VIDEO_GAME`, только производитель у него не поток, а
отдельная программа: `bare_app_doom` из `ports/doom/` (doomgeneric, GPLv2), клиент VCMI
(`vcmiclient`, GPLv2) и движок Xash3D, которые собирают пакеты SDK со своими патчами
связи с bare_app, `bare_app_wine` для Windows-игр, любая SDL2-игра. Каждая игра
начинается в новом процессе: Doom хранит состояние в глобальных переменных и выходит
через `exit()`, VCMI просто большой. Падение игры не роняет приложение, а GPL-код не
линкуется в `bare_app`.

### Реестр игр

Игру описывает одна `struct game_def` в её файле `games/<игра>.c` (`games/game.h`), а
`games/games.c` перечисляет их строкой на игру, в порядке меню. Меню, экран игры и ядро
view знают игры только через эту таблицу: switch по играм нигде нет.

| Поле | Что даёт |
|---|---|
| `id`, `title`, `hint` | имя в логе, пункт меню и заголовок, подсказка с кнопками после первого кадра |
| `entries(rescan)` | сколько пунктов у игры, найденных во время работы (Windows-игры, игры из `game.ini`); без него — один |
| `info(entry, &gi)` | своё имя пункта, подсказка, триггеры (Windows-игра называется по `wine.ini`) |
| `missing(entry)` | чего не хватает для запуска (путь), экран пишет это вместо ошибки |
| `start(entry, &env)` | запуск: размер слоя, PCM-устройство, язык, платформа |
| `trigger_volume` | L2/R2 меняют громкость, а не идут в игру |
| `hint_for(pf)`, `minimize_for(pf)` | подсказка и кнопка сворачивания по платформе (Герои на GO Ultra: F1) |

Пункт меню хранит `struct game_ref` (игра и номер пункта). Меню выбирает его
`view_game_select()` и открывает `SCREEN_GAME`. Экран берёт `view_game_selected()` и
вызывает `view_video_set(VIDEO_GAME)`: та же игра продолжается из свёрнутой, другая
сначала закрывает свёрнутую. `view_game()` возвращает игру в слое, по ней меню
ставит значок паузы, а F5 снова открывает её экран. Пока игра в слое, её пункты не
ищутся заново (`entries(false)`), чтобы номер пункта не сдвинулся.

Каждая игра включает символ `GAMES` в Kconfig, по нему собираются общие части:
`games/games.c`, `games/game_proc.c`, `screens/game.c`.

Общее для адаптеров игр — в `games/game_proc.h`: `game_setting()` (путь из Kconfig,
который подменяет переменная окружения), `struct game_vars` (окружение игры поверх
окружения bare_app, `game_vars_sdl_audio()` для звука SDL), `game_proc_mkdir()`,
`game_proc_alsa_name()`. Что игре надо знать о плате, платформа говорит строками
`"игра.ключ=значение"` в `game_opts` (`homm3.keys=ogu`, `halflife.renderer=soft`), а
читает их сама игра через `platform_opt()`: в `struct platform` нет полей конкретных
игр.

В образе игру включает одна опция пакета bare-app в `APPS_CONFIG` прошивки
(`bare-app.HOMM3=y`): пакет собирает движок и передаёт bare_app
`-DBARE_APP_CONFIG_EXTRA="CONFIG_GAME_HOMM3=y;..."`, эти строки ложатся поверх
defconfig. Отдельно включать игру в defconfig bare_app нужно только для сборки без
Buildroot.

Сторону игры реализует `games/game_ipc_client.h` (только заголовок, C и C++):
`game_link_open()`, `game_link_frame()`, `game_link_publish()`, `game_link_recv()`. Им
пользуются `ports/doom`, `ports/wine` и драйверы SDL; у VCMI и Xash3D своя копия в
их патчах. `game_ipc.h`, `game_ipc_client.h` и `core/input.h` пакет bare-app ставит в
`$(STAGING_DIR)/usr/include/bare_app/`, оттуда их берут пакеты игр. Эти два
заголовка — под MIT: они компилируются в игры с любой лицензией.

Граница лицензий держится так же, как граница с LVGL: GPL-код есть только в `ports/doom/`
и в пакете `vcmi` SDK, а собираются из них отдельные исполняемые файлы. Через границу
проходят только пиксели и события геймпада (`GP_*`, оси) по протоколу
`games/game_ipc.h`. Заголовки игр `bare_app` не подключает, поэтому их управление и
логику меню знают только сами игры. Сам протокол читают и C, и C++ (VCMI).

```
игра ── кадр в размер слоя → memfd (3 буфера, атомарный обмен)
  ▲                               │ GAME_MSG_FRAME (сокет SEQPACKET)
  │ GAME_MSG_BUTTON, GAME_MSG_AXIS ▼
games/game_proc.c (поток view): game_proc_frame → копия в слой → DRM-плоскость; EOF → waitpid
```

- `games/game_proc.c` — общая часть: запускает игру через `posix_spawn` с пустой маской
  сигналов (в приложении сигналы заблокированы ради signalfd) и с дополнительными
  переменными окружения. Сокет и memfd игра получает как дескрипторы 3 и 4.
  `start` каждой игры только собирает аргументы, окружение и рабочий каталог и
  проверяет, что есть данные.
- Тройной буфер обходится без мьютекса: каждая сторона меняет свой буфер на средний
  через `atomic_exchange`. Игра, упавшая посреди кадра, не может заблокировать поток view.
- Повторяющиеся кадры игры не отправляют: `TryRunTics` в Doom рисует примерно вдвое
  чаще тиков, VCMI перерисовывает экран с постоянной частотой.
  Вместо такого кадра игра шлёт `GAME_MSG_FRAME` с флагом `GAME_FRAME_SAME`
  (`game_link_same()`): ничего не публикуется, но ядро view засчитывает кадр, и над
  неподвижной картинкой частота кадров остаётся частотой игры (Doom — раз в тик,
  VCMI — патч 0013). Игра, которая так не умеет, над неподвижной картинкой молчит:
  для неё пауза дольше `FRAMETIMES_IDLE_US` (250 мс) — не фриз, а простой
  (`view_video_paced()`); Xash3D публикует каждый кадр (`game_def.every_frame`).
- Кнопки уходят без автоповтора. У направления, которое дал левый стик, а не
  крестовина, стоит флаг `GAME_BTN_STICK` (в `gp_event` — поле `stick`): Doom
  его не различает, а VCMI двигает курсор осями стика и не прокручивает от него карту.
- Экран `screens/game.c` общий для игр. Он прозрачный, захватывает геймпад и передаёт
  события в `view_video_input()`. До первого кадра (`view_video_frames()`) на нём
  написано «Загрузка...», потом, если включено в настройках (`game_hint`), всплывает
  подсказка с кнопками. Когда игра
  заканчивается сама, ядро view вызывает `view_video_on_end()`: при коде 0 экран
  закрывается, иначе показывает причину. Чего не хватает для запуска (IWAD, VCMI,
  данные Героев), экран тоже пишет.

### Своё управление игры

`core/remap` — таблица «кнопка устройства → кнопка для игры» (`struct gp_remap`) и её
текст в файле настроек (`a=b,b=a,x=-`). `ctl_settings` держит таблицы игр в
`settings.controls` контекста (до `CONTROLS_MAX`, только отличные от исходной) и в
конфиге под `controls.<game_key()>`, меняет их по `ACT_SET_CONTROL` и
`ACT_RESET_CONTROLS`. Экран игры применяет таблицу из снимка контекста
(`ctx_controls()`) к кнопкам после тех, что оставляет себе (сворачивание, громкость), к
направлениям стика — нет. Редактор — `screens/controls.c` (`SCREEN_CONTROLS`, игра из
`view_game_selected()`), его открывает X на плитке игры.

### Игры из game.ini и SDL2

`games/native.c` (`GAME_NATIVE`) делает пунктом меню каждый `<каталог>/<игра>.ini` и
`<каталог>/<игра>/game.ini` из `GAME_NATIVE_DIRS`. В файле программа, аргументы, что
нужно для запуска, подсказка, раскладка и переменные окружения; формат описан в
`docs/game.ini`. Игра получает свой каталог данных `<GAME_NATIVE_DATA>/<игра>` как HOME
и рабочий каталог, звук через `AUDIODEV` платформы и `SDL_VIDEODRIVER=bareapp`.

SDL2-игре больше ничего не нужно. SDL2 SDK собирается с драйверами `bareapp` (пакет
bare-app, `APPS_CONFIG += bare-app.SDL=y`, патч в `package/bare-app/sdl2/`):

- видео: окно любого размера вписывается в кадр слоя (пропорции, чёрные поля;
  `SDL_BAREAPP_SCALE`, `SDL_BAREAPP_FILTER`), режим рабочего стола — размер слоя.
  Программный кадр копируется, OpenGL ES рисует GPU в pbuffer размера окна (EGL
  surfaceless Mesa) и читается при каждом swap. Темп не больше `SDL_BAREAPP_FPS`
  (60) кадров в секунду, как vsync;
- джойстик: геймпад bare_app — один `SDL_GameController` со своей раскладкой (кнопки по
  надписям, F1 start, F2 back; `SDL_BAREAPP_GAMEPAD`), оси стиков, L2/R2 как триггеры.
  Драйвер Linux при этом не открывает evdev (подсказка `SDL_JOYSTICK_LINUX=0`): там те
  же кнопки;
- кнопки как клавиши по `SDL_BAREAPP_KEYS` для игр без поддержки контроллера;
- когда bare_app закрывает сокет, игра получает `SDL_QUIT`.

Драйверы включаются сами, когда процесс получил дескрипторы bare_app, и только если
`SDL_VIDEODRIVER` не называет другой драйвер. VCMI запускается с `dummy` и читает сокет
сам, его это не касается.

### Герои III (VCMI)

- `games/homm3.c` запускает `GAME_HOMM3_PROGRAM` с `SDL_VIDEODRIVER=dummy`,
  `XDG_*_HOME` в `GAME_HOMM3_DATA` (данные игры в `<dir>/vcmi`, настройки в
  `<dir>/config/vcmi`) и звуком через alsa-lib (`AUDIODEV=plughw:C,D` из
  `platform.game_pcm`), язык интерфейса передаёт в `BARE_APP_LANG` (`i18n_lang()`).
  Обработчики сигналов SDL выключены: SIGTERM завершает игру сразу, иначе VCMI
  спросил бы «выйти?».
- Связь на стороне VCMI (патч пакета `vcmi`, `client/renderSDL/BareAppLink.cpp`)
  ставит окно в два раза больше слоя (960×640 при слое 480×320), программный рендер
  и программный курсор. После каждого `SDL_RenderPresent` содержимое окна уходит в
  слой уменьшенным 2:1 (среднее четырёх пикселей) или куском 1:1 вокруг курсора
  («лупа»); L1 переключает.
- Кнопки и стик VCMI получает как события SDL-геймпада (`SDL_PushEvent`), поэтому
  курсор, клики и горячие клавиши ведёт его собственная поддержка контроллера и её
  раскладка (`config/keyBindingsConfig.json`). Карту приключений крестовина
  прокручивает напрямую (связь отдаёт её направление `AdventureMapInterface`), в
  остальных окнах изображает правый стик (жест прокрутки списков), в лупе двигает
  лупу до следующего движения стика. Прокрутка у края экрана требует наклона стика
  к этому краю. L2/R2 игре не передаются: экран игры bare_app меняет ими громкость
  (`game_def.trigger_volume`; Half-Life и Windows-игры триггеры оставляют себе).

Нюанс LVGL: при ARGB-дисплее тема делает нижний слой (`lv_layer_bottom`)
непрозрачным, поэтому бэкенд после установки темы явно делает его прозрачным.

## Сетка экранов

Все экраны раскладываются по одной сетке (`widgets/console.c`): экран делится на
`UI_ROWS` (16) квадратных клеток по высоте (`ui_cell()`: 20 пикселей на OGA, 30 на
GO Ultra), по ширине — сколько целых клеток влезает, а остаток делится пополам между
краями, поэтому поля слева и справа одинаковые (`ui_margin()`: клетка плюс половина
остатка). Шапка — две верхние строки, подвал с подсказками кнопок — две нижние, тело
(`ui_body_area()`, `screen_body()`) — между ними с отступом в полклетки. Размеры не из
целых клеток задаются в пикселях раскладки 480×320 и масштабируются `ui_px()`.

- `console_screen()` — фон, шапка (строка состояния без подложки, от поля до поля),
  линия под ней; `footer_create()`/`footer_set()` — линия и подсказки «(B) Назад
  (A) OK»; `console_row()` — строка списка в две клетки с рамкой фокуса внутри.
- Главный экран: название выбранного с 2,25 клетки, плитки 7×7 клеток с клетки 4 через
  клетку, круглые кнопки в 1,5 клетки с 12-й.
- Настройки: разделы шириной 7 клеток, линия посередине следующей клетки, пункты
  дальше до поля; раздел и пункт по 2 клетки, поэтому стоят вровень.
- Тест ввода — схема геймпада 22×11 клеток посередине тела: курки сверху, крестовина
  и левый стик слева, X Y A B и правый стик справа, остальные кнопки и значения стиков
  в середине; показываются только кнопки и стики, которые объявил драйвер.

## Шрифты и языки

- Строки интерфейса лежат в `gui/view/core/i18n.c` (таблица en/ru, `tr(S_*)`),
  модуль не зависит от тулкита. Язык задаётся при запуске (`-L ru`,
  `BARE_APP_LANG`), по умолчанию английский. Control строк не формирует, например
  неизвестная модель платы приходит в контекст пустой строкой.
- Шрифты `gui/view/lvgl/fonts/ui_font_{14,20,28}.c`: Noto Sans (OFL) с латиницей,
  кириллицей и типографскими знаками. Размер выбирает `ui_font()` по экрану: мелкий и
  средний — 14 и 20 пикселей на экране высотой 320 (OGA), 20 и 28 при клетке сетки от
  26 пикселей (GO Ultra, 480 строк). Монитор системы плотный и всегда пишет 14
  пикселями (`UI_TEXT_COMPACT`). Их генерирует `tools/gen_font.py`, ему нужны
  только Python и Pillow, без `lv_font_conv`/npm. Значки `LV_SYMBOL_*` берутся из
  встроенного Montserrat того же размера через `fallback`.

## Звук и Wi-Fi

Микшер и Wi-Fi устроены как питание: драйвер → сервис (публикует в шину) →
control-модуль (секция контекста) → экраны.

- Звуки интерфейса (`services/sound.c`, сейчас один: сигнал при смене громкости)
  играет свой поток через `hal_pcm_ops` (`drivers/pcm_alsa.c`, ioctl без alsa-lib).
  Запросы, пришедшие во время звука, склеиваются в один. Устройство открыто, пока идут
  звуки, и закрывается через секунду после последнего: без dmix оно у ALSA
  монопольное, а Doom выводит звук в него же. Doom при `EBUSY` ждёт до 2 с.
- Звук Doom живёт в GPL-порте (`ports/doom/doom_sound.c`), не в bare_app: модуль
  `sound_module_t` движка смешивает эффекты (DMX-сэмплы 8 бит, линейная интерполяция до
  48 кГц) в своём потоке. Устройство bare_app передаёт аргументом (`-pcm` из
  `platform.game_pcm`, без него `-nosound`), так что граница по-прежнему проходит
  только через кадры, кнопки и командную строку.

- Сервис микшера следит за fd драйвера (события ALSA: штекер, `amixer` в shell) и
  публикует состояние только при изменении. `audio_get()` отдаёт последнее
  опубликованное, а не читает драйвер: чтение забирает события.
- Громкость в процентах — по кривой alsamixer (корень кубический из амплитуды), поэтому
  после записи она читается обратно с точностью до шага микшера. Кнопки громкости
  шагают дальше, пока уровень реально не сдвинется, и показывают его (`NOTIFY_VOLUME`,
  окно поверх всего). Кнопки громкости ядро view обрабатывает до захвата геймпада,
  поэтому они работают и в игре.
- Сервис Wi-Fi переподключается к демону каждые 3 с, пока тот не ответит (демон
  стартует позже приложения, перезапускается, на плате без чипа его нет), и раз в 3 с
  перечитывает состояние: об адресе от DHCP демон событий не шлёт. Вкл/выкл — это
  `DISCONNECT`/`RECONNECT` демона, настройка применяется при каждом подключении к нему.
- Подключение: `SELECT_NETWORK` отключает остальные сети. Они включаются снова, когда
  выбранная подключилась, отвергла ключ или не подключилась за 30 с. Новый ключ
  всегда идёт в новую запись, и старые записи той же сети удаляются только после
  успешного подключения, после чего `SAVE_CONFIG`. Ключ проходит view → control →
  драйвер в `gui_action.secret`, в лог не пишется, буфер действия затирается.
- Адрес — дело системы. В образе OGA `wpa_cli -a /etc/wpa_cli.action` (из `S41wifi`)
  продлевает аренду udhcpc при повторном подключении к той же сети и перезапускает
  клиент при подключении к другой.
- Ввод ключа — `lv_keyboard`. Порт ввода отдаёт Up/Down самой кнопочной матрице,
  когда она в фокусе, а X — как `UI_LV_KEY_ALT` (событие `LV_EVENT_KEY` у объекта
  в фокусе): на клавиатуре это «стереть», в списке сетей — «забыть».

## Трансляция (RTSP)

`stream/` (`CONFIG_STREAM`, нужен OpenH264) — свой RTSP-сервер без сторонних
библиотек RTSP: `stream.c` (запросы OPTIONS, DESCRIBE с SDP, SETUP для UDP и TCP
interleaved, PLAY, PAUSE, TEARDOWN, GET_PARAMETER; клиенты, потоки), `rtp.c` (пакеты
H.264 по RFC 6184 — одиночные NAL и FU-A, L16, RTCP SR + SDES; без сети, покрыт тестом),
`h264.c` (OpenH264: XRGB → I420 BT.601, кадр → access unit в Annex B).

- Владеет трансляцией ядро view: по `settings.stream` контекста (`ACT_SET_STREAM`,
  `stream=` в конфиге) запускает и останавливает её, а таймер 30 раз в секунду, пока
  есть зритель, сводит слои дисплея (операция `layers` HAL, `media/shot.c:
  shot_compose()`) в кадр ящика (`media/mailbox`). Те же `layers` дают снимок экрана.
- Поток сети (poll: приём соединений, запросы, ящик кадров, RTCP зрителей) кодирует
  кадр и рассылает пакеты. Перед кадром для TCP-зрителя проверяется место в сокете
  (`SIOCOUTQ`): не влезает — кадр этому зрителю пропускается и следующим идёт
  ключевой, пакет никогда не обрывается на середине.
- Поток звука читает захват loopback (`pcm_alsa` научился `read`) по 10 мс, шлёт L16
  зрителям и пишет то же на устройство. Игры получают устройство через `game_pcm()`
  ядра view: при включённой трансляции — сторону воспроизведения loopback.

## Монитор системы

Удержание F5 ловит ядро view до захвата геймпада, как кнопки громкости, поэтому
монитор открывается и над игрой. Нажатие F5 придерживается, пока не ясно, что это:
через 600 мс ядро шлёт `ACT_SYSMON`, а если F5 отпустили раньше, нажатие и отпускание
уходят дальше обычным путём (`deliver()`: захват экрана игры или клавиши UI). Поэтому
короткое F5 срабатывает при отпускании.

- `services/sysmon.c` читает `/proc` и `/sys`: что не меняется (политики cpufreq и
  имена ядер из `CPU part`, зоны `thermal`, devfreq GPU, батарея, диски) — один раз
  при открытии, значения и счётчики — на каждом замере. Загрузки и скорости считаются
  между двумя замерами, у первого они неизвестны (-1). Все пути идут от корня, который
  тест подменяет поддельным деревом (`test_sysmon`).
- `ctl_sysmon` открывает его по `ACT_SYSMON 1`, сразу делает первый замер, второй
  через 400 мс, дальше раз в секунду; по `ACT_SYSMON 0` закрывает. Скрытый монитор
  ничего не читает.
- Виджет `widgets/sysmon.c` стоит на `lv_layer_top` с запуска и виден, пока
  `sysmon.shown`. Строки он строит при показе и заново, когда меняется их набор
  (запустилась игра, появился диск); значения обновляет только при отличии. Тексты
  его не переводятся (не в `i18n`), монитор всегда на английском.
  Кадры игры берёт у ядра view (`view_video_frame_times()`); строка FPS и график
  есть, только пока игра на экране. График — линия времени кадра за 10 с со шкалой
  50/100/200 мс (растёт по худшему кадру), пунктир — 60 и 30 кадров/с, фризы
  красным, простой игры без `GAME_FRAME_SAME` — тусклая линия внизу и «still»
  вместо частоты.

## Снимки экрана

`kill -USR1 <pid>` → control → уведомление `NOTIFY_SNAPSHOT` → ядро view вызывает
`snapshot` дисплея. Файл берётся из `BARE_APP_SHOT`, по умолчанию
`/tmp/bare_app.ppm`. С `BARE_APP_SHOT` снимок пишется и при выходе, до разборки UI.
Это снимок буферов приложения, а не того, что реально на панели; что именно
выводится, видно в `/sys/kernel/debug/dri/0/state`. `tools/oga.sh shot` делает
снимок через сигнал.

## События ядра

`core/uevent` — netlink-сокет `NETLINK_KOBJECT_UEVENT` с фильтром по подсистеме,
отдельный на каждого потребителя, в цикле его потока:

- сервис питания перечитывает батарею по событию `power_supply` (плюс опрос раз
  в 30 с: не каждый драйвер шлёт событие на изменение заряда);
- `input_evdev` ищет устройство заново по `input add` (повтор каждые 100 мс, пока
  mdev создаёт узел), а при пропаже устройства отпускает его кнопки и обнуляет оси.

## Конфигурация сборки

Состав бинарника задаёт Kconfig (`Kconfig`, `configs/*_defconfig`, `cmake/kconfig.cmake`):

- при конфигурировании CMake из defconfig получается `<build>/.config`, а
  `genconfig` пишет `<build>/bare_app_config.h`. Заголовок подключается ко всем
  исходникам bare_app (`-include`), но не к LVGL;
- значения `CONFIG_*` попадают и в CMake: по ним выбираются исходники (драйверы,
  платформы, экраны, шрифты), а в коде `#ifdef CONFIG_*` убирает ссылки на
  выключенное (таблицы платформ, меню, список бэкендов, таблица переводов);
- зависимости описаны в Kconfig: экран «Layers» включает тестовый источник видео,
  русский язык требует шрифтов с кириллицей, платформа OGA включает evdev и fbdev,
  если DRM выключен;
- что есть у устройства, решается во время работы: драйверы объявляют кнопки и оси
  (`input_declare`), экран теста ввода показывает только их.

Новый модуль подключается так: символ в `Kconfig` → строка `add_if(CONFIG_X ...)` в
`CMakeLists.txt` → `#ifdef CONFIG_X` там, где на модуль ссылаются (платформа, меню).

## Как расширять

Добавление игр с примерами — в [GAMES.md](GAMES.md).

| Задача | Что сделать |
|---|---|
| Новая плата с уже поддержанным железом | `src/platforms/<board>.c` (таблицы + compatible), строка в `platforms[]` в hal/platform.c, символ `PLATFORM_<BOARD>` в Kconfig |
| Новый тип устройства того же класса (DRM вместо fbdev, тачскрин) | драйвер в `src/drivers/`, ссылка на него из платформы |
| Новый класс оборудования (LED, звук, GPIO) | ops в hal.h → драйвер → поле в `struct platform` → сервис (публикует в шину) → control-модуль (секция контекста) → виджеты |
| Новый экран | `widget_ops` в `gui/view/lvgl/screens/`, id в `enum screen_id`, строка в `screen_ops[]` |
| Новая SDL2-игра | `game.ini` (`docs/game.ini`) в `/usr/share/bare_app/games/` или в каталоге игры на `/games`; код bare_app не меняется |
| Новая игра со своей связью | программа (своя лицензия) с протоколом `games/game_ipc.h`, по образцу `ports/doom/doom_main.c`; `games/<игра>.c` с `struct game_def`, строка в `games/games.c`, символ `GAME_<ИГРА>` с `select GAMES` в Kconfig, `add_if()` в CMakeLists.txt, строки в i18n |
| Другой тулкит | новый каталог `gui/view/<backend>/` с `view_backend_ops`; остальное не меняется |
