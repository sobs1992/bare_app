# Архитектура bare_app

## Цели

1. Своё приложение для SDK с выводом через LVGL; первая платформа — ODROID-GO Advance
   (экран, кнопки, стик).
2. Новая плата или новое оборудование добавляются без переделки остального кода.
3. LVGL отвечает только за отрисовку и может быть заменён другим тулкитом.

## Слои

```
┌──────────────────────────────────────────────────────────────────┐
│ gui/view/<backend>   виджеты и экраны тулкита (lvgl, headless)    │  единственное место с LVGL
├──────────────────────────────────────────────────────────────────┤
│ gui/view/core        поток view: снимки контекста, подписки,      │  без тулкита
│                      геймпад → UI-клавиши, захват ввода           │
├──────────────────────────────────────────────────────────────────┤
│ gui/ctx · action · notify   граница между control и view          │  без тулкита
├──────────────────────────────────────────────────────────────────┤
│ gui/control          модули по областям данных: питание, экран,   │  без тулкита
│                      звук, Wi-Fi, навигация, система              │
├──────────────────────────────────────────────────────────────────┤
│ services · core      шина событий, главный цикл, очереди,         │
│                      логический геймпад, математика стика         │
├──────────────────────────────────────────────────────────────────┤
│ hal (интерфейсы) · drivers (реализации) · platforms (таблицы)     │
└──────────────────────────────────────────────────────────────────┘
```

Границу с тулкитом держит сборка: путь к заголовкам LVGL подключён только к цели
`bare_app_view_lvgl`. Подключение `lvgl.h` в любом другом месте ломает сборку.
Бэкенд `headless` собирается вообще без тулкита и служит проверкой этой границы.

## Потоки

| Поток | Владеет | Ждёт в `poll()` |
|---|---|---|
| control (main) | сервисы, шина, модули control, запись в контекст | signalfd, очередь шины, очередь действий, таймеры сервисов |
| view | LVGL, драйверы экрана и ввода, подписки view, видео-слой | eventfd контекста, очередь notify, evdev, DRM, ящик кадров, таймеры LVGL |
| источники видео | свой буфер в ящике кадров | свой темп (камера, таймер) |
| процесс `bare_app_doom` | движок Doom, свой буфер в общей памяти | свой цикл, 35 тиков/с |

Потоки control и view работают каждый на своём экземпляре `core/mainloop`. Между
потоками общих объектов пять, все потокобезопасные:

- контекст `gui_ctx` (мьютекс; view читает только снимки);
- очередь действий view → control (`gui_action_post`);
- очередь уведомлений control → view (`gui_notify_post`);
- шина событий: сервисы → control (`bus_post`, можно из любого потока);
- ящик кадров: источник видео → view (`media/mailbox`).

Сигналы (SIGINT, SIGTERM, SIGHUP) заблокированы во всех потоках и принимаются
через `signalfd` в потоке control. Если программа упадёт по SIGSEGV и т. п.,
драйвер fbdev вернёт консоль в `KD_TEXT`.

## Поток данных

```
 сервис ──bus──► control-модуль ──ctx_lock/unlock──► gui_ctx ──снимок──► подписки view ──► LVGL
                       ▲                                                     │
                       └───────────────── gui_action_post ◄──────────────────┘
                       └──► gui_notify_post ──► view (тосты, без склейки)
```

- **Контекст** — это снимок состояния, в нём только значения: проценты, флаги,
  `enum`. Цвета, иконки и готовый текст в контекст не кладутся. Секции
  (`CTX_POWER`, `CTX_DISPLAY`, `CTX_NAV`, `CTX_SYSTEM`, `CTX_SETTINGS`, `CTX_AUDIO`,
  `CTX_WIFI`) — единицы изменения.
  `ctx_unlock(mask)` будит view, а view берёт снимок один раз за итерацию. Поэтому
  несколько записей между двумя кадрами приходят как одно изменение с последними
  значениями.
- **Действия** — единственный способ для view что-то изменить. В контекст view
  не пишет.
- **Уведомления** — разовые события («батарея разряжена», «зарядка подключена»).
  Они не склеиваются, доставляется каждое.
- **Ввод** через контекст не идёт. Поток view сам читает evdev: навигацию передаёт
  в тулкит, а глобальный хоткей выхода — в control как действие. Экран может
  захватить сырой геймпад (`view_input_grab`), так работает тест ввода.

## Модули control

control делится по областям данных, а не по виджетам: каждый модуль пишет только
свою секцию.

| Модуль | Слушает | Пишет |
|---|---|---|
| `ctl_app` | `ACT_QUIT` | останавливает цикл control |
| `ctl_nav` | `ACT_OPEN_SCREEN`, `ACT_BACK` | `CTX_NAV` (стек экранов) |
| `ctl_system` | — | `CTX_SYSTEM` (платформа, модель из DT) |
| `ctl_power` | `EV_POWER_CHANGED` | `CTX_POWER`, уведомления |
| `ctl_display` | `ACT_SET_BRIGHTNESS` | `CTX_DISPLAY` (то, что подсветка реально приняла) |
| `ctl_audio` | `EV_MIXER_CHANGED`, `ACT_SET_VOLUME`, `ACT_VOLUME_STEP`, `ACT_SET_AUDIO_OUT` | `CTX_AUDIO`, `NOTIFY_VOLUME`; в режиме «авто» переключает выход по штекеру |
| `ctl_wifi` | `EV_WIFI_*`, `ACT_WIFI_*` | `CTX_WIFI` (связь, адрес, сети рядом), уведомления о подключении и неверном ключе |

Каркас модуля: `struct control_ops { init, on_action, deinit }` (gui/control/control.h).

## Виджеты view

Каркас виджета (gui/view/lvgl/widget.h):

```c
struct widget_ops {
	const char *name;
	uint32_t deps;                                          /* секции контекста */
	void *(*init)(lv_obj_t *parent, lv_obj_t **root);       /* создать объекты */
	void  (*update)(void *self, const struct gui_ctx *ctx, uint32_t changed);
	void  (*deinit)(void *self);
};
```

- `widget_create()` вызывает `init`, подписывает `update` на `deps` (первый вызов
  сразу, с `CTX_ALL`) и привязывает отписку и `deinit` к удалению корневого объекта.
- `update` сравнивает новое значение с показанным и только при отличии вызывает
  `lv_*_set_*`: каждый вызов set перерисовывает область.
- Экраны тоже виджеты. Менеджер экранов следит за `CTX_NAV` и даёт каждому экрану
  свою группу фокуса.
- Один виджет можно ставить на несколько экранов: строка состояния
  (`statusbar_create`) стоит на всех.

## HAL, драйверы, платформы

- **hal/hal.h** — интерфейсы: дисплей со слоями (`LAYER_VIDEO`, `LAYER_UI`,
  `LAYER_OSD`), ввод, питание, подсветка, микшер, Wi-Fi. Буфер слоя хранится в логической
  ориентации, формат (XRGB или ARGB) выбирает драйвер, поворот делает драйвер.
  Необязательная операция `snapshot` пишет сложенные слои в PPM.
- **drivers/** — реализации:
  - `display_drm` — DRM/KMS на голых ioctl ядра (без libdrm): UI на overlay-плоскости
    в ARGB, видео на primary, по два dumb-буфера на слой, nonblocking atomic commit
    не чаще одного на vblank (событие flip в цикле view), поворот и premultiply при
    копировании изменённых областей (`blit.c`);
  - `display_fbdev` — один слой UI, поворот как у fbcon; запасной вариант, если DRM
    занят или его нет;
  - `display_mem` — экран в памяти для тестов, у платформы `pc-mem` с видео-слоем
    под UI, как на OGA;
  - `sdl` — окно и клавиатура симулятора (платформа `pc`);
  - `input_evdev` — поиск по имени, раскладка, калибровка осей по `EVIOCGABS`,
    hotplug по uevent; `input_script` — сценарий кнопок из stdin;
  - `sysfs` — батарея и подсветка; `console.c` — KD_GRAPHICS и его возврат, в том
    числе при падении;
  - `mixer_alsa` — ioctl управляющего устройства ALSA без alsa-lib: регуляторы по
    имени, кривая громкости по dB-диапазону (как в alsamixer, `core/volume.c`), выбор
    выхода, штекер, события изменений;
  - `wifi_wpa` — управляющий сокет `wpa_supplicant` без libwpa_client: запросы с
    таймаутом и второй сокет (ATTACH) для событий;
  - `sim` — имитация микшера и Wi-Fi для платформ ПК.
- **platforms/** — только данные: какие драйверы и с какими параметрами.
  `platform_probe()` выбирает платформу по `/proc/device-tree/compatible`.
  Дисплеев в платформе можно указать несколько, открывается первый рабочий
  (на OGA: DRM, затем fbdev).
  Поэтому ревизии OGA 1.0, 1.1 и Super работают из одного бинарника, а размер
  экрана берётся у драйвера.

Логический геймпад (core/input) отделяет физические коды от смысла:
evdev-код → `GP_*` (раскладка платформы) → UI-клавиша (view core) → `LV_KEY_*` (бэкенд).
Стик превращается в виртуальную крестовину с гистерезисом. Автоповтор направлений
делается здесь же, а не в LVGL: indev LVGL работает в режиме событий, без опроса.

## Видео-слой

Слой `LAYER_VIDEO` лежит под UI. Экран, который показывает видео, делает свой фон
прозрачным и выбирает источник через ядро view: `view_video_set(VIDEO_TEST_PATTERN)`.

Источники работают в своих потоках и отдают кадры через `media/mailbox`:

```
поток источника ── mailbox_begin / mailbox_end ──► mailbox (3 буфера) ── eventfd ──►
поток view: mailbox_take → копия в слой → damage / submit → DRM-плоскость
```

Источник никогда не ждёт. Непрочитанный кадр заменяется более новым, и для видео
это правильно: важен последний кадр. Пока источник один — `media/testpattern.c`,
поток с собственным темпом кадров. Камера (V4L2) или GPU-рендер подключаются так же.
Чтобы избежать лишней копии, им понадобится импорт dmabuf прямо в плоскость.

Если видео-слоя нет (fbdev, SDL), `view_video_available()` возвращает false, и экран
показывает сообщение. Пример — экран «Layers».

## Игры: Doom в отдельном процессе

Doom (`GAME_DOOM`) — ещё один источник видео, `VIDEO_DOOM`, только производитель у него
не поток, а отдельная программа `bare_app_doom` из `ports/doom/` (doomgeneric, GPLv2).
Движок хранит состояние в глобальных переменных и выходит через `exit()`, поэтому
каждую игру он начинает в новом процессе. Падение игры не роняет приложение, а GPL-код
не линкуется в `bare_app`.

Граница лицензий держится так же, как граница с LVGL: GPL-код есть только в `ports/doom/`,
а его CMake-цель — отдельный исполняемый файл. Через границу проходят только пиксели и
коды кнопок `GP_*`. Заголовки doomgeneric `bare_app` не подключает, поэтому клавиши Doom
и логику меню знает только игра.

```
bare_app_doom ── кадр 320×200 → масштаб в размер слоя → memfd (3 буфера, атомарный обмен)
      ▲                                     │ DOOM_MSG_FRAME (сокет SEQPACKET)
      │ DOOM_MSG_BUTTON                     ▼
games/doom.c (поток view): doom_frame → копия в слой → DRM-плоскость; EOF → waitpid
```

- `games/doom.c` запускает игру через `posix_spawn` с пустой маской сигналов (в
  приложении сигналы заблокированы ради signalfd). Сокет и memfd игра получает как
  дескрипторы 3 и 4, рабочий каталог — `GAME_DOOM_DIR`.
- Тройной буфер обходится без мьютекса: каждая сторона меняет свой буфер на средний
  через `atomic_exchange`. Игра, упавшая посреди кадра, не может заблокировать поток view.
- Повторяющиеся кадры игра не отправляет (`TryRunTics` рисует примерно вдвое чаще
  тиков).
- Экран `screens/doom.c` прозрачный. Он захватывает геймпад и передаёт события в
  `view_video_input()`. Кнопки в клавиши Doom переводит сама игра: она видит состояние
  меню и оружие игрока. Когда игра заканчивается сама, ядро view вызывает
  `view_video_on_end()`. При коде 0 экран закрывается, иначе показывает причину.

Нюанс LVGL: при ARGB-дисплее тема делает нижний слой (`lv_layer_bottom`)
непрозрачным, поэтому бэкенд после установки темы явно делает его прозрачным.

## Шрифты и языки

- Строки интерфейса лежат в `gui/view/core/i18n.c` (таблица en/ru, `tr(S_*)`),
  модуль не зависит от тулкита. Язык задаётся при запуске (`-L ru`,
  `BARE_APP_LANG`), по умолчанию английский. Control строк не формирует, например
  неизвестная модель платы приходит в контекст пустой строкой.
- Шрифты `gui/view/lvgl/fonts/ui_font_{14,20}.c`: Noto Sans (OFL) с латиницей,
  кириллицей и типографскими знаками. Их генерирует `tools/gen_font.py`, ему нужны
  только Python и Pillow, без `lv_font_conv`/npm. Значки `LV_SYMBOL_*` берутся из
  встроенного Montserrat того же размера через `fallback`.

## Звук и Wi-Fi

Микшер и Wi-Fi устроены как питание: драйвер → сервис (публикует в шину) →
control-модуль (секция контекста) → экраны.

- Звуки интерфейса (`services/sound.c`, сейчас один: сигнал при смене громкости)
  играет свой поток через `hal_pcm_ops` (`drivers/pcm_alsa.c`, ioctl без alsa-lib).
  Запросы, пришедшие во время звука, склеиваются в один. Устройство открыто, пока идут
  звуки, и закрывается через секунду после последнего: без dmix оно у ALSA
  монопольное, а Doom выводит звук в него же. Doom при `EBUSY` ждёт до 2 с.
- Звук Doom живёт в GPL-порте (`ports/doom/doom_sound.c`), не в bare_app: модуль
  `sound_module_t` движка смешивает эффекты (DMX-сэмплы 8 бит, линейная интерполяция до
  48 кГц) в своём потоке. Устройство bare_app передаёт аргументом (`-pcm` из
  `platform.game_pcm`, без него `-nosound`), так что граница по-прежнему проходит
  только через кадры, кнопки и командную строку.

- Сервис микшера следит за fd драйвера (события ALSA: штекер, `amixer` в shell) и
  публикует состояние только при изменении. `audio_get()` отдаёт последнее
  опубликованное, а не читает драйвер: чтение забирает события.
- Громкость в процентах — по кривой alsamixer (корень кубический из амплитуды), поэтому
  после записи она читается обратно с точностью до шага микшера. Кнопки громкости
  шагают дальше, пока уровень реально не сдвинется, и показывают его (`NOTIFY_VOLUME`,
  окно поверх всего). Кнопки громкости ядро view обрабатывает до захвата геймпада,
  поэтому они работают и в игре.
- Сервис Wi-Fi переподключается к демону каждые 3 с, пока тот не ответит (демон
  стартует позже приложения, перезапускается, на плате без чипа его нет), и раз в 3 с
  перечитывает состояние: об адресе от DHCP демон событий не шлёт. Вкл/выкл — это
  `DISCONNECT`/`RECONNECT` демона, настройка применяется при каждом подключении к нему.
- Подключение: `SELECT_NETWORK` отключает остальные сети. Они включаются снова, когда
  выбранная подключилась, отвергла ключ или не подключилась за 30 с. Новый ключ
  всегда идёт в новую запись, и старые записи той же сети удаляются только после
  успешного подключения, после чего `SAVE_CONFIG`. Ключ проходит view → control →
  драйвер в `gui_action.secret`, в лог не пишется, буфер действия затирается.
- Адрес — дело системы. В образе OGA `wpa_cli -a /etc/wpa_cli.action` (из `S41wifi`)
  продлевает аренду udhcpc при повторном подключении к той же сети и перезапускает
  клиент при подключении к другой.
- Ввод ключа — `lv_keyboard`. Порт ввода отдаёт Up/Down самой кнопочной матрице,
  когда она в фокусе, а X — как `UI_LV_KEY_ALT` (событие `LV_EVENT_KEY` у объекта
  в фокусе): на клавиатуре это «стереть», в списке сетей — «забыть».

## Снимки экрана

`kill -USR1 <pid>` → control → уведомление `NOTIFY_SNAPSHOT` → ядро view вызывает
`snapshot` дисплея. Файл берётся из `BARE_APP_SHOT`, по умолчанию
`/tmp/bare_app.ppm`. С `BARE_APP_SHOT` снимок пишется и при выходе, до разборки UI.
Это снимок буферов приложения, а не того, что реально на панели; что именно
выводится, видно в `/sys/kernel/debug/dri/0/state`. `tools/oga.sh shot` делает
снимок через сигнал.

## События ядра

`core/uevent` — netlink-сокет `NETLINK_KOBJECT_UEVENT` с фильтром по подсистеме,
отдельный на каждого потребителя, в цикле его потока:

- сервис питания перечитывает батарею по событию `power_supply` (плюс опрос раз
  в 30 с: не каждый драйвер шлёт событие на изменение заряда);
- `input_evdev` ищет устройство заново по `input add` (повтор каждые 100 мс, пока
  mdev создаёт узел), а при пропаже устройства отпускает его кнопки и обнуляет оси.

## Конфигурация сборки

Состав бинарника задаёт Kconfig (`Kconfig`, `configs/*_defconfig`, `cmake/kconfig.cmake`):

- при конфигурировании CMake из defconfig получается `<build>/.config`, а
  `genconfig` пишет `<build>/bare_app_config.h`. Заголовок подключается ко всем
  исходникам bare_app (`-include`), но не к LVGL;
- значения `CONFIG_*` попадают и в CMake: по ним выбираются исходники (драйверы,
  платформы, экраны, шрифты), а в коде `#ifdef CONFIG_*` убирает ссылки на
  выключенное (таблицы платформ, меню, список бэкендов, таблица переводов);
- зависимости описаны в Kconfig: экран «Layers» включает тестовый источник видео,
  русский язык требует шрифтов с кириллицей, платформа OGA включает evdev и fbdev,
  если DRM выключен;
- что есть у устройства, решается во время работы: драйверы объявляют кнопки и оси
  (`input_declare`), экран теста ввода показывает только их.

Новый модуль подключается так: символ в `Kconfig` → строка `add_if(CONFIG_X ...)` в
`CMakeLists.txt` → `#ifdef CONFIG_X` там, где на модуль ссылаются (платформа, меню).

## Как расширять

| Задача | Что сделать |
|---|---|
| Новая плата с уже поддержанным железом | `src/platforms/<board>.c` (таблицы + compatible), строка в `platforms[]` в hal/platform.c, символ `PLATFORM_<BOARD>` в Kconfig |
| Новый тип устройства того же класса (DRM вместо fbdev, тачскрин) | драйвер в `src/drivers/`, ссылка на него из платформы |
| Новый класс оборудования (LED, звук, GPIO) | ops в hal.h → драйвер → поле в `struct platform` → сервис (публикует в шину) → control-модуль (секция контекста) → виджеты |
| Новый экран | `widget_ops` в `gui/view/lvgl/screens/`, id в `enum screen_id`, строка в `screen_ops[]` |
| Новая игра | программа в `ports/<игра>/` (своя лицензия) рядом с `bare_app` по образцу `ports/doom/doom_main.c` (тот же протокол или свой), источник в `games/`, значение в `enum video_source`, экран по образцу `screens/doom.c` |
| Другой тулкит | новый каталог `gui/view/<backend>/` с `view_backend_ops`; остальное не меняется |
